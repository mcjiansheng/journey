## 一、范围与结论

- **动态验证**（`node` 直接执行，未用 npm）：
  - 以 in-process `createApp` 起真实服务并走 API：`create activity` patch 含 `ordinal` → `422 {"code":"VALIDATION","message":"Unrecognized key: \"ordinal\""}`；去掉 `ordinal`（改用 `order`）→ `200`。
  - 币种：trip.currency=KRW、一笔已支付 150000 KRW，`widgetModel` 得 `formattedTotal ₩1,500`、`formattedPer ₩750`；同数据按 `ui.money`/`currencyFactor` 口径为 `₩150,000`。
  - 对比度：白字 on 正午渐变起点 `#3d92e2` = 3.28:1；中号右栏玻璃面板（#ffffff26 叠在起点上）≈ 2.71:1；门禁脚本检查的是 `#2f7abc` = 4.53:1。
  - 时差：device Asia/Shanghai → 目的地 Asia/Kolkata 显示「慢 2 小时」（实际 2.5h）；Kathmandu 2.25h 也被四舍五入为 2h。
  - 性能：2030 objects 快照下，20 个 day/route 小组件单次重算 18ms，100 个 activity 小组件 7ms。
  - 未跑浏览器 E2E（只读与环境约束）；E2E 现状引用 Lead 的 `06-验证记录.md`，下文按 spec 代码判断覆盖。
- **结论**：无 P0。**2 条 P1**：费用小组件对 KRW 等非 JPY 零小数币种金额缩小 100 倍（与费用页不一致）；地点小组件「加入行程」必败并污染本地视图（与 01 报告 P1-1 同源，本报告补地点数据丢失与按钮锁死两点）。**5 条 P2**：正午日程小组件对比度不达标且门禁假通过；时钟时差被取整到小时；日期区间超 365 天时按钮禁用却无提示；倒计时/费用「今天」跨午夜不刷新；小组件层缺 memo（与 01 P2-6 同源，附量化）。**9 条 P3** 为标记色暗色对比度、radius token 失效、`widgetDeps` 死代码与口径漂移、`dayLabel` 未判空、时区缺失降级、reduced-motion 秒针、已移除文案、`bufferBefore=0` 与默认月份 UTC。
- **总体**：小组件「不存数据、每次现算」的架构、7 种小组件的字段口径、MapSketch 的种子/投影，以及 `CONTRACT.md` 的 mark/preset 全部语义（服务端级联、名称不改、删除保留、mark 独立时钟、null→star/amber、新收藏恒 null）均与契约一致；问题集中在资金口径、视觉/门禁、时区细节与性能实现（`widgetDeps` 未接线）。

### 02-01（P1）费用小组件对 KRW 等币种金额缩小 100 倍

- **代码路径**：`board-widgets.js:478` 汇总 `amountMinor`（最小货币单位）；`money()`（`domain.js:186-192`）只把 JPY 视为 0 位小数，其余一律 `/100`；`ExpenseWidget.jsx:14` 又手写了一遍同样的 `cur === 'JPY' ? 1 : 100`。而 Ledger 用的是 `ui.money`＋`currencyFactor`（`ui.jsx:238-249,271-277`，由 `Intl…maximumFractionDigits` 决定，KRW=1、CNY/USD=100、KWD=1000），`domain.money` 目前的唯一调用方就是新的 `board-widgets.js`。
- **复现**：创建旅程时币种选 KRW（`Entry.jsx:274` 的币种列表含 KRW）→ 费用页记一笔「已支付 150000 KRW」（`currencyFactor('KRW')===1` → `amountMinor=150000`）→ 白板贴费用小组件。实测 `widgetModel.formattedTotal = ₩1,500`、`formattedPer = ₩750`、中号「花得最多」行 `₩1,500`；费用页同数据是 `₩150,000`、人均 `₩75,000`。
- **影响**：主数字、人均、TOP4、预计金额全部少报 100 倍，与费用页/账单直接矛盾，用户会低估已支付预算；JPY 正常、KWD 等 3 位小数币种（API 可设）被放大 10 倍。
- **依据**：`docs/设计文档/10-白板.md` §4.8「主数字取整到元（与费用页『已支付合计』同口径）」；`CONTRACT.md` expense.payment 最小单位定义。
- **建议**：`board-widgets.js`/`ExpenseWidget.jsx` 统一改用 `ui.money` 与 `currencyFactor`（或把 `domain.money` 改为 `currencyFactor` 版本并只保留一个实现）；补 KRW/JPY/CNY 三组单测（当前 `board-widgets.test.mjs` 只测 CNY）。

### 02-02（P1）地点小组件「加入行程」必现失败并污染本地视图（与 01 P1-1 同源，补充三点）

- **代码路径**：`Board.jsx:582-607`：`patch` 里带 `ordinal: 99`（`:599`）和只含 `name` 的 `placeData`（`:587-591`），随后 `patchBoardItem(linkedActivityId)`（`:606`）。`schemas.activity` 是 `.strict()` 且无 `ordinal`（`model.mjs:78`），`applyOperation` 的 `parse`（`model.mjs:143`）→ `422 VALIDATION`（已用真实 API 实证）。`linkedActivityId` 再触发 `INVALID_REFERENCE`（`model.mjs:119`）。两个失败操作进入 `op.blocked` 并 `pausedTrips.add(op.tripId)`（`sync.js:895-897`），该旅程后续修改全部停在本机队列。
- **本报告补充（01 未覆盖）**：① 收藏地点小组件的 `content` 只有 `favoriteId`，回退出的 `placeData` 只有 `{name}`——即使修掉 `ordinal`，创建的安排也会丢经纬度/地址/类别，地图上无法定位；② `mutate` 的本地乐观投影不过滤阻塞项（`sync.js:326-343`），点完按钮白板会立刻显示「已安排 · 第1天」、行程页出现幽灵活动，但服务端从未创建 → 本机与同伴视图不一致；③ `patchBoardItem` 先写本地 items 与 IndexedDB 缓存（`board-sync.js:504-525`），`linkedActivityId` 已落本地，操作条「加入行程」因该字段非空而永久消失，用户只能去同步面板重试/丢弃。
- **依据**：`10-白板.md` §4.5/§7 地点小组件操作条；`CONTRACT.md` activity payload 与 boardItem `linkedActivityId` 条款。
- **建议**：去掉 `ordinal`（用 `order`）；`placeData` 从 favorite payload 取完整 Place 并剥掉 `mark`；两步操作串接失败时回滚本地 `linkedActivityId` 并给出行内提示；补 E2E「贴地点小组件 → 加入行程 → 行程页出现带坐标的活动且小组件显示已安排」。

### 02-03（P2）正午日程小组件对比度不达标，校验脚本假通过

- **代码路径**：`board.js:221-222` 正午档 `{a:'#3d92e2', b:'#1f5fb4'}`；`ActivityWidget.jsx:48-56` 用 `model.sky.a/b` 作背景，`widgets.css` 中 `.w { color:#fff }`，胶囊 11.5px、地点 12px、右栏辅助 11–12.5px；`.right` 玻璃面板 `#ffffff26`+blur 叠在渐变上。`check-design-contrast.mjs:23-36` 的 `skyGradients` 正午/下午两行写的是 `#2f7abc`/`#3a77b3`，与实现值不一致。
- **复现**：活动开始时间 11:00–13:59（`hourOf` 返回 11–13.99）→ 贴日程小组件。实测白字 on `#3d92e2` = **3.28:1**，on 叠加 15% 白的玻璃面板 ≈ **2.71:1**；而门禁脚本对 `#2f7abc` 测得 4.53:1 并输出通过。
- **影响**：设计 §5.4 明文「所有小组件上的小字（<18px）对其底色须 ≥4.5:1」，正午时段全天的日程小组件小字不达标；对比度门禁对 2/7 组渐变实际失效，掩盖回归。
- **依据**：`10-白板.md` §5.4 对比度条款（并要求「用 `check-design-contrast.mjs` 对上表每个渐变的两端都检查一次」）。
- **建议**：正午起点加深到 ≥4.5（如脚本现值 `#2f7abc`），或将玻璃面板改为不可再提亮的半透明黑；门禁脚本的渐变值改为从 `board.js` 导出常量（或在脚本中断言与实现一致），并让 06 把它接入 dev 门禁。

### 02-04（P2）时钟时差被四舍五入到整小时

- **代码路径**：`board-widgets.js:447-457`：以 `toLocaleString('en-US',{timeZone})` 的墙钟字符串相减再 `Math.round(.../3600000)`。
- **复现**：设备 Asia/Shanghai、旅程目的地为印度（timezone Asia/Kolkata）→ 中号时钟显示「比你这里慢 2 小时」（实际 2 小时 30 分）；Kathmandu +5:45 被显示为 2 小时。
- **影响**：旅行工具的核心信息之一（当地时间/时差）错误，且在 M 规格固定展示；半小时区/45 分区（印度、尼泊尔、阿德莱德等）全部受影响。
- **依据**：`10-白板.md` §4.8 clock 中号「与本机的时差」。
- **建议**：改为分钟差并输出「慢 2 小时 30 分」，或用 `Intl.DateTimeFormat` 的 `timeZoneName:'longOffset'` 求偏移差；补 Kolkata/Kathmandu×Shanghai 单测（现有测试只覆盖整小时）。

### 02-05（P2）超过 365 天的日期区间让流程静默卡死

- **代码路径**：`DateRangePicker.jsx:38-50` 对任意两次点击都直接 `onChange(min,max)`，无长度约束；`Itinerary.jsx:430` `valid = count>=1 && count<=365`；按钮 `disabled={!valid || selectingRange}`（`:599-605`）；错误文案只在 `finish()` 内抛（`:444-459`），而 `valid=false` 时按钮不可点 → 文案永远不会出现。
- **复现**：行程页「当天操作 → 调整日期与天数」→ 日历选 2026-11-01、再点 2027-11-02（367 天）→ 「完成/下一步」变灰，无提示、无错误文本，用户只能猜测。
- **影响**：日期调整主路径在越界选择时无反馈地卡住；与 CONTRACT「dayCount 1–365」和 11-03 §五「用日历选开始和结束」的可用性要求不符。
- **依据**：`CONTRACT.md` trips 条款（dayCount 1–365）；`docs/评审输入/2026-11-03-…修改建议-2026-11-03.md` §五。
- **建议**：picker 接收最大天数（超出时禁用日期或截断并提示），或在 Reschedule 显示行内错误「旅程最长 365 天」并始终展示当前选择天数；补 >365 天 E2E（现有 E2E 只测跨月/反向/键盘）。

### 02-06（P2）倒计时与费用「今天」跨午夜不自动刷新

- **代码路径**：`board-widgets.js:359-429` 用传入的 `now`（`BoardWidget` 渲染时 `Date.now()`）算 `todayIso` 与 diff；`:496-508` 用同样方式算费用重点柱 `hi`。`widgets/index.jsx:13-39` 无任何定时器，`CountdownWidget.jsx` 也无（对照：`Itinerary.jsx:718` 有 60s now 定时器，说明项目已有先例）。
- **复现**：白板页保持打开跨过目的地 00:00（旅行中移动端常驻页面很常见）→ 倒计时数字/进度点、费用「今天」重点柱仍停在前一天，直到用户产生任一交互（选中、平移、同伴 presence）触发重渲染。
- **影响**：「距出发/旅途中第几天」差一天，属于跨天信息错误且不易察觉。
- **依据**：`10-白板.md` §4.9 明确把「目的地时区的今天」列为 countdown、expense 的重绘依赖；§4.7 diff 规则。
- **建议**：在 BoardWidget 或 Board 层加按目的地时区对齐的 60s 定时器（今天变化才 setState），或接 4.9 的 memo 时把 today 纳入依赖并定时刷新。

### 02-07（P2）小组件缺 memo，2000 项画布拖动/平移重算明显（与 01 P2-6 同源）

- **代码路径**：`BoardItem.jsx:94` 每次渲染都执行 `BoardWidget → widgetModel`；`Board.jsx:262` 拖动/缩放的每个 pointermove 都 `setRemoteLive` 触发整板重渲染（`Board.jsx:653-665` 的视口裁剪后仍全量 map）；`board-widgets.js:69` 的 `widgetDeps` **全仓无 UI 调用**（仅 `board-widgets.test.mjs` 引用），与设计 §4.9/§7「按 widgetDeps 序列化值 memo，变化才重建」不符。
- **量化**（本机 node 基准，2030 objects 快照）：20 个 day/route 小组件 → 18ms/次重算；100 个 activity 小组件 → 7ms；单个 day/route 模型约 0.9ms（同日 50 项时 `findLegRoute` 对全对象线性扫描 × 相邻对）。拖动/平移每帧都会触发一次。
- **影响**：2000 项上限画布上拖动、画线、缩放掉帧；同时这也是 02-10 的修复前提（否则接上 memo 会带来不刷新问题）。
- **建议**：`React.memo(BoardItem)` + 按 `widgetDeps` 序列化值 `useMemo(widgetModel)`（先修 02-10 的依赖缺项）；把 live 位移改到独立覆盖层或直接改 transform（与 01 建议一致）。

## 三、需求一致性

1. **小组件数据口径（§4）**：复用 `orderedActivities`/`timeLabel`/`dayLabel`/`travelAdvice`/`money`/`expenseDate`/`expenseTitle`/`visibleDays` 全部符合 §4.2；`mark` 为 null 时用 `{icon:'star',color:'amber'}`（`board-widgets.js:258,267,297-298`）符合 §4.2。偏差：金额换算（02-01）、时区缺失降级（02-12）、跨天刷新（02-06）；route 模型内部用 `fromId/toId` 而 §4.6 定义 `fromN/toN`（`board-widgets.js:316-324`），仅输出结构命名差异，`MapSketch` 内部自洽。
2. **示意地图（§5.6）**：种子哈希/随机数/绘制顺序与文档逐项一致（`board.js:233-259`）；投影公式（`board.js:155-182`，经度乘 cos 平均纬度、按外接框等比居中）符合 §4.6；颜色全取 map token。同一坐标的多站投影后重合（`s=0` 时落在框中心），文档未规定小组件内的展开行为，需复核（非缺陷）。
