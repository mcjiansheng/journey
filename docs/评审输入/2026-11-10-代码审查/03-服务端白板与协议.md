## 一、范围与结论

- 未发现 P0（无鉴权绕过、无 RCE、无正常路径数据损坏）。
- 鉴权/授权基本正确：board / boardItem / presence / assets 全部先 `withMember`；跨旅程 `boardId`、`objectId`、`linkedActivityId` 均被旅程隔离（代码路径：`model.mjs:107,113,150` 与 `index.mjs:96` 均带 `tripId` 过滤；探针：非成员/跨旅程读 items → 403；测试覆盖跨旅程活动引用 → `INVALID_REFERENCE`）；新路由走同一全局 Origin+CSRF 中间件（探针：无 CSRF 的 presence / asset PUT → 403 `CSRF_REJECTED`）。
- 路径注入不可行：`id` 为 `^[A-Za-z0-9_-]+$`（`model.mjs:6`），tripId 必须先过 membership，assetId 先过 `id.safeParse`，`resolve()` 拼接不会被 `..` 逃逸。
- 上传类型判定、`nosniff`、`private, immutable` 缓存头与设计一致（探针：PNG 字节 + `Content-Type: text/html` 仍按文件头存为 `image/png`，GET 返回 `image/png` + `nosniff` + `immutable`）。
- 增量协议语义正确（探针：create/patch/delete/restore 后 `?since=` 恰好返回被改项且 `changedCursor > since`；跨 board 不串；`epoch` 正确返回）。
- **主要风险集中在限流/presence 资源上限与素材落盘、备份、部署配置**（P1 共 4 条）。

## 二、缺陷表

### S-01［P1］presence 上行耗尽全局 IP 限额，连续拖拽约 31 秒后整个 API 被 429
- 位置：`app/server/index.mjs:54`（`rate('ip:'+req.ip,500,60000)`，所有 API 共用）、`app/server/index.mjs:97`（presence 每设备 15 次/秒）；客户端 `app/src/board-sync.js:414`（节流 60ms≈16.7 次/秒）、`app/src/components/Board.jsx:260`（每次 pointermove 调 `sendPresence`）。
- 触发路径（探针实测）：同一设备按客户端真实节流 60ms/次发 presence。第 **932ms/第 16 次**即触发 `PRESENCE_RATE`（16.7/s > 15/s，超出部分客户端 `board-sync.js:410` 静默丢弃）；持续 60ms/次时第 **499 次/31.25s** 触发全局 `RATE_LIMITED`，此后 `GET /api/trips/:id` 与 `POST /operations`（保存白板元素）均为 429，直到固定窗口（60s）结束。两名成员同 NAT/办公网共享同一 IP 时更快。
- 影响：白板主要交互（拖动/缩放）+ 正常保存路径在持续操作约半分钟后整体不可用；客户端连续 3 次失败会把 presence 标为离线，操作进入重试/离线队列。契约写明"15 次/秒/设备"，但该速率在 500 次/分/IP 的全局桶下根本不可能持续。
- 建议：把 presence 从全局 IP 桶分离（独立 `presence:user` 桶，或 15/s 之外再加每用户窗口）；全局上限按页面实际请求量评估上调（如 2000/min）；客户端节流改为 ≥67ms 或服务端上限调到 20/s；`RATE_LIMITED` 需在客户端区分"仅 presence 失败"与"API 不可用"。

### S-02［P1，若按"生产不可用"口径可升 P0］presence 与 SSE 无资源上限，可被低权限用户 OOM
- 位置：`app/server/index.mjs:97`（`live:z.record(id,frame)` 无键数/体积上限；`checkIds` 对每个键做一次 DB 查询）、`:101`（15s 清理只在**存在该旅程 SSE 流**时才跑；无流时永不清理）、`:21`/`:56`（`broadcastPresence`/`notify` 对每个 stream 无上限 `res.write`，忽略背压；`streams` 无每用户/每旅程连接数上限）、`app/server/model.mjs:13-18`（frame 恒定小对象）、`app/ops/journey.service:36-37`（`MemoryMax=512M`）。
- 攻击路径：(1) 注册任意账号 → 自建旅程（新旅程自带 `default-board`）；(2) 以 500 请求/分/IP 的节奏在 4 分钟内创建 2000 个 boardItem（每板 active 上限正好 2000）；(3) 循环 `POST /boards/default-board/presence`，body 为 2000 键的 `live`（约 170KB，<2MB JSON 限制）且每次换一个 `deviceId`（限流键含 deviceId，可自选），**不打开该旅程 SSE**（清理路径不触发）；每次请求 2000 次 DB 校验 + 约 0.4–1MB 常驻内存（V8 解析对象），500 次/分 → 数百 MB/分，数分钟内 OOM/被 systemd 重启。(4) 放大变体：用第二个账号在同一旅程挂大量 SSE 连接（SSE 建连只受 IP 500/min 约束，`LimitNOFILE=4096`），成员 A 每次 presence 向全部连接同步写大 payload，单请求可向 socket 缓冲写入数百 MB。
- 影响：任意注册用户即可让服务端内存/CPU 耗尽，进程重启（数据不丢但服务中断，可重复）。
- 建议：`live` 键数上限（如 ≤200）与请求体上限；presence 只接受 `selected/editing` 等小字段时不做逐键 DB 校验（或先按白板一次性查 id 集合）；增加**与 SSE 无关**的全局清理定时器（按 `at` 清理、删除空 tripMap）；限制每用户/每旅程 SSE 连接数、presence 条目总量；`res.write` 检查返回值或对大 payload 限流；对 `deviceId` 加服务端可信标识（如与 clock lease 绑定）。

### S-03［P1，需复核］素材目录未纳入备份，灾难恢复后白板图片全部丢失
- 位置：`app/ops/backup.mjs:43-63`（`createBackup` 只快照 `main`/`security` 两个 SQLite 文件；`restoreBackup` 同）、`docs/设计文档/10-白板.md:210`（明确要求"纳入 `ops/backup.mjs`"）、`:211`（无总量上限但保留配额）。
- 触发路径：生产按 `journey-backup.timer` 定期备份 → 灾难恢复只还原 DB → boardItem `content.image.assetId` 仍存在但 `data/assets/<tripId>/...` 全部缺失 → `GET assets` 404，白板所有图片/GIF 裂图且不可恢复。
- 影响：素材是用户上传的原始内容，属可感知数据丢失；同时 `app/data/assets` 未纳入 `ReadWritePaths`（见 S-04）意味着恢复也无法写回。
- 建议：备份/恢复包含 assets 目录（打包进同一加密备份或单独加密+校验和清单）；恢复前校验 assetId 引用完整性。归属上同时请 06 复核 ops。

### S-04［P1，需复核生产实际配置］生产 nginx/systemd 与素材上传能力不匹配
- 位置：`app/ops/journey.nginx.conf:9`（`client_max_body_size 2m`）、`app/ops/journey.service:9`（`WorkingDirectory=/opt/journey/current`）、`:21`（`ReadWritePaths=/var/lib/journey`）、`:22`（`ProtectSystem=strict`）；实现侧 `app/server/index.mjs:99` 落盘 `resolve(options.assetsDir||'data/assets', tripId)`（相对 cwd，且 `config.mjs` 无 assetsDir 配置项）。
- 触发路径：按仓库配置部署时，① GIF 允许到 5MB（`index.mjs:99`），但 2MB–5MB 的 GIF 在 nginx 即被 413（返回 HTML，客户端 `api()` JSON 解析失败）——设计主打的"GIF 原文件上传"对常见 2MB+ GIF 不可用；② assets 写入 `/opt/journey/current/data/assets`，在 `ProtectSystem=strict` 且未列入 `ReadWritePaths` 时是只读挂载 → `mkdirSync`/`writeFileSync` 抛错，资产 PUT 统一 500。
- 影响：若生产 unit/nginx 与本仓库一致，白板图片/GIF 功能在线上不可用（至少 >2MB GIF 必坏）。
- 建议：nginx 提高 `/api/trips/*/assets/*` 的上限（如 6m，其余保持 2m）；把素材目录做成可配置项（`ASSETS_PATH`）指向 `/var/lib/journey/assets` 并补 `ReadWritePaths`/`StateDirectory`；与 06、部署负责人确认生产实际 unit/nginx 版本。

### S-05［P2］无素材总量/配额与孤儿清理，可写满磁盘
- 位置：`app/server/index.mjs:99`（仅每用户 60 次/分）；`docs/设计文档/10-白板.md:179`、`:211`（设计了 `ASSET_QUOTA` / `ASSET_QUOTA_BYTES`，实现中完全不存在）；删除 boardItem / 删除 board / 上传后 create 失败均不清理素材文件；客户端每次重试 `uploadAsset` 都生成新 assetId（`board-sync.js:198-201`），失败重试会持续产生孤儿。
- 触发/影响：任一成员 60×5MB/分 ≈ 300MB/分写盘（多成员并行更快），无总量上限、无回收 → 磁盘耗尽导致整站 500（SQLite WAL 也写不进去）。
- 建议：实现 `ASSET_QUOTA_BYTES`（按旅程累计）与孤儿回收（按 boardItem 引用清扫，或软删除后定时清理）；上传前先 create 占位再上传，或 create 失败时回滚删除素材。

### S-06［P2］默认白板懒创建：GET 有写副作用、不推进 cursor、不通知，且未写入契约
- 位置：`app/server/index.mjs:79`（建旅程时 `ensureDefaultBoard`）、`:96`（GET items 兜底）、`:97`（presence 兜底）、`app/server/model.mjs:99-105`；`app/CONTRACT.md:20-24` 与设计文档均未定义 `default-board`。
- 触发路径（探针）：直接向 DB 注入旧旅程（模拟 origin/main 已存在的旅程）→ `GET /boards/default-board/items` 会 `INSERT` 一块 board，但 `trips.cursor` 0→0、无 `notify`。其他成员的快照/白板列表直到下一次写操作才可能出现该板；GET 由只读语义变成写库。另：旧旅程首次以 `objectId='default-board'` 建 boardItem 会先插板再插同 id 行，触发主键冲突 → 500（探针实测，见 S-10）。
- 影响：迁移期多设备列表不一致；只读 GET 触发写、影响备份/复制的幂等假设；`default-board` 成为未文档化的协议外固定对象。
- 建议：在版本迁移或建旅程事务内显式创建默认板（并 `next`+`notify`），GET/presence 去掉写操作；把 `default-board` 写入 CONTRACT 与设计文档，或改由客户端创建。

### S-07［P2］永久清除在 DB 事务内删除素材目录，文件与数据库不一致
- 位置：`app/server/index.mjs:84`（`remove()` 事务内 `rmSync(resolve(assetsDir,t),{recursive:true,force:true})`）。
- 触发路径：最后一名成员退出触发 purge；`rmSync` 成功后在事务提交前若安全账本 checkpoint/COMMIT 失败（磁盘满、ledger 写失败），`transaction()` 回滚 → **旅程仍在但素材已全部删除**；反之 `rmSync` 抛错（权限/IO）会让最后成员无法退出（500）。文件删除也不可回滚。
- 影响：罕见失败下的素材丢失或无法退出旅程。
- 建议：事务只做 DB 删除，提交成功后再删目录并容错（记录待清理队列）；素材删除失败不应阻塞业务。

### S-08［P2］容量上限只统计 active，墓碑（tombstone）无上限，增量/查询成本线性增长
- 位置：`app/server/model.mjs:125`、`:181`（`state='active'` 计数）、`app/server/index.mjs:96`（无 since 全量返回含 deleted；since 查询按 trip+kind 扫描后逐行 `json_extract`）、`app/server/db.mjs:32`（索引 `(tripId,kind,changedCursor)` 不含 boardId）。
- 触发路径：任一成员反复"创建→删除"同一白板元素，active 恒 ≤2000 但行数无上限；`GET items`（无 since，或 epoch 变化后的全量重读）返回所有墓碑，响应体与客户端内存随历史线性增长；`since` 查询与 presence 的逐键校验都随历史变慢。契约说明"软删除保留、不做到期清理"，但未说明总量上界。
- 影响：长期使用的白板会明显变慢/变大；同时让 S-02 的 `live` 可用 id 集合可超 2000（墓碑也算 boardItem 行）。
- 建议：为 boardItem 增加总量/墓碑上限或按产品决定清理策略；`items` 支持分页/`changedCursor` 上限；索引改为含 boardId 的表达式索引或冗余列。

### S-09［P3］超限请求体返回 `INTERNAL_ERROR` + 英文内部信息，与 `ASSET_TOO_LARGE` 契约不符
- 位置：`app/server/index.mjs:45`（全局 `express.json` 2mb）、`:98`（`express.raw({limit:'5mb'})`）、`:106`（错误处理 `code:err.code||'INTERNAL_ERROR'`，非 500 直接透传 `err.message`）。
- 探针：5MB+10B 的 body → `413 {code:'INTERNAL_ERROR', message:'request entity too large'}`。客户端据 code 分支（如重试/提示）会走错路径，且向用户暴露英文内部信息。
- 建议：把 body-parser 的 `entity.too.large` 映射为 `ASSET_TOO_LARGE`/`VALIDATION` 与中文提示；`limit` 与契约上限对齐（GIF 5MB 应留头空间）。

### S-10［P3］旧旅程以 `default-board` 作 boardItem id 触发未处理的主键冲突 500
- 位置：`app/server/model.mjs:99-105`（references 内先建默认板）+ `:148`（同 id 插入 boardItem）。
- 探针（旧旅程、未 GET 过 items）：`create boardItem objectId='default-board', boardId='default-board'` → `500 ERR_SQLITE_ERROR`，事务回滚无数据损坏，但客户端得到 500 而非 `OBJECT_EXISTS`/`VALIDATION`。
- 建议：create 前统一检查 `objects.tripId+id` 是否已被任何 kind 占用（含默认板）；`ensureDefaultBoard` 后重新走 id 冲突分支。

### S-11［P3］已删除的 boardItem/board 在板满时 patch 被误判 BOARD_FULL
- 位置：`app/server/model.mjs:125`、`:162`（patch 也执行容量校验，计数排除自身但按 active 计）；board 同类问题在 `:108-111`。
- 触发路径：某板已有 2000 个 active 元素时，patch 一个已删除元素（契约允许编辑隐藏对象）→ 计数 2000 ≥ 2000 → `BOARD_FULL`；对已删除 board 改标题同理（20 块 active 时）。提示与原因不符。
- 建议：容量校验仅对 create/restore 生效，或按"变更后 active 总数"判断。

### S-12［P3］`since` 非法值静默退化为全量
- 位置：`app/server/index.mjs:96`（`Number(req.query.since)`，`NaN`/负数/数组直接忽略过滤器）。
- 探针：`?since=abc` 返回全量。客户端拼错时无任何提示，可能把全量当增量合并；也不会报错。
- 建议：`since` 用 `z.coerce.number().int().nonnegative()` 校验，非法返回 422；负数视为全量需显式文档化。

### S-13［P3］items 返回对象缺少 `tripId`（快照对象有），与 CONTRACT 的 Object 形状不一致
- 位置：`app/server/index.mjs:96`（只 SELECT `id,kind,payload,state,generation,clocks,changedCursor`）vs `app/CONTRACT.md:20`（Object 含 `tripId`、`expressions?`）。
- 影响：客户端若复用快照对象的归一化/缓存逻辑，tripId 为 undefined；当前 `normalizeBoardItem` 不依赖它，但契约与实现需对齐（补字段或修契约）。

### S-14［P3］设计/契约与实现的状态码、配置项不一致
- `docs/设计文档/10-白板.md:169-181` 错误码表写 `VALIDATION`/`INVALID_REFERENCE` 为 400，实现统一 422（`model.mjs:5` 默认 422，测试也断言 422）；`ASSET_QUOTA`（`:179`）/`ASSET_QUOTA_BYTES`（`:211`）未实现；`ASSET_CONFLICT`/`ASSET_TYPE` 只写在设计文档、未写进 CONTRACT；`GET items` 未写入 CONTRACT 的错误语义（非法 since）。
- 建议：以实现为准统一文档（或补实现），至少 CONTRACT 与设计文档的码表必须一致，避免客户端按错误码分支时踩坑。

### S-15［P3］presence 发送者按 session token 排除，同账号多标签页互不可见
- 位置：`app/server/index.mjs:21`（`s.tokenHash!==senderTokenHash`）。
- 影响：同一账号开两个标签页（共享 Cookie/session）时，一个标签页的拖动 `live` 不会推给另一个标签页；与设计"只发给同旅程的其他连接"的语义有偏差（"连接"被实现为"会话"）。数据同步不受影响，仅在线态显示。
- 建议：按连接 id（而非 tokenHash）排除发送连接，或明确该行为。

### S-16［P3，需复核］board 的删除/恢复权限与设计表述需对齐
- 位置：`app/server/model.mjs:176-189`；设计 `docs/设计文档/10-白板.md:160-168`（第 5 步"board 保持现有规则（管理员团队由管理员删，平等团队走表态）"）。
- 现状：boardItem 任意成员可删/恢复（符合 CONTRACT:21）；board 删除走通用规则（创建者，或 admin 团队的管理员），恢复仅创建者/管理员，equal 团队实际只有创建者能恢复；对 board 的 `express` 可写入，但阈值仅在 `teamMode==='equal'` 时触发（`:197`）。"平等团队走表态"对恢复是否适用，文档未写清。
- 建议：与产品确认 board 删除/恢复/表态矩阵并写进 CONTRACT；若按现有规则，补齐测试。

## 三、协议/需求一致性核对

| 契约/设计条款 | 实现 | 结论 |
| --- | --- | --- |
