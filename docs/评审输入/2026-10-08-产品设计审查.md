# 多人协作旅行规划工具：产品需求与现有设计审查

我的结论：你们的设计文档在软件工程层面比较完善，但产品设计仍然存在一些明显的改进空间。

我逐份检查了压缩包中的 7 份 Markdown 文档，重点核对了功能需求（FR-01～FR-17）、业务规则、数据模型、用户旅程、交互设计和验收计划。

目前最大的风险并非缺少某几个页面，而是：

1. 规划过程偏正式化。 用户需要较早确定日期和具体时间，而现实中大家通常先收集想法，再逐渐明确安排。
2. 协作机制偏向组织者。 系统允许成员表达意见，但部分权限和决策规则可能阻碍真正的平等参与。
3. 可执行性与现实需求之间有缺口。 行程有时间、位置、费用，却缺少预订状态、任务责任人等影响真实出行的重要信息。
4. 部分版本和投票规则过于严格。 用户正常编辑行程，可能产生不必要的投票失效和保存冲突。
5. 三人团队的交付范围过大。 17 组功能加上完整的安全、性能、恢复和跨端验收，存在明显的进度风险。

这些问题并不意味着原设计不能使用。相反，现有文档已经建立了很好的工程基础。建议保留整体架构，主要调整产品模型和关键交互。

## 一、真正好用的多人旅行工具应该提供什么？

我对照了 Wanderlog、Mindtrip 和 Google Maps 的协作收藏能力。

Wanderlog 已经覆盖共同编辑、行程、地图、路线、预订资料、预算分摊和离线查看；Mindtrip 侧重从旅行灵感、朋友协作到行程和预订资料的完整衔接。

这说明你们不能仅靠“共同收藏地点”和“共享行程表”形成鲜明的产品价值。

我认为最有价值的方向是：

帮助一个有不同偏好、时间限制和预算的朋友小组，更轻松地形成一份所有人都理解、能够实际执行的旅行计划。

按照真实的使用过程，我建议组织成以下功能体系。

| 功能模块  | 用户真正需要的能力            | 推荐优先级 |
| ----- | -------------------- | ----- |
| 旅行空间  | 创建、邀请、成员管理、基础设置      | 核心    |
| 灵感收集  | 地点搜索、链接收集、收藏、去重、标注   | 核心    |
| 偏好与约束 | 想去程度、时间限制、预算约束、参与意愿  | 核心    |
| 行程规划  | 按天安排、拖拽排序、灵活时间、地图、交通 | 核心    |
| 协作与沟通 | 实时更新、对象评论、变更摘要、投票、提醒 | 核心    |
| 可行性检查 | 时间冲突、路程、营业、预算、预订信息   | 核心    |
| 方案管理  | 多方案对比、决定记录、确认版本、恢复   | 核心    |
| 预订与任务 | 待预订状态、负责人、确认信息、截止时间  | 建议新增  |
| 出行模式  | 今日行程、导航、临时修改、只读离线备份  | 高     |
| 费用管理  | 总预算、费用明细、个人费用、实际支出   | 高     |
| 导入与导出 | 行程分享、PDF、日历、攻略链接导入   | 高     |
| 智能辅助  | 路线优化、智能推荐、AI 协商与替代建议 | 后续    |

这里的“核心”是从真实产品体验出发的优先级，不代表所有功能都必须在这次课程开发中一次完成。

## 二、我认为最值得修改的 5 个核心问题

### 1. 缺少真正灵活的行程规划机制

高优先级

现有设计： `01-FR-05` 要求日程节点具有明确的开始和结束时间；`03` 中 `PlanItem` 也以 `start`、`end` 为主要字段。创建旅行时还必须先确定日期。

这套逻辑适合精确排程，但不完全符合大多数朋友旅行从模糊想法逐步形成计划的过程。

例如，四个人决定周六去南京，最开始可能只知道：

- 上午想去博物馆。
- 中午在附近吃饭。
- 下午考虑玄武湖。
- 晚上已经预约餐厅，必须 18:30 到达。

只有最后一项具备严格时间约束。

我建议允许三种不同的安排状态：

候选地点

尚未安排

先锋书店 · 想去的人 3/4

已安排到某天

时间灵活

南京博物院 · 周六上午 · 建议游玩 2 小时

固定时间

已锁定

晚餐预约 · 周六 18:30–20:00 · 不随普通拖拽移动

这样用户可以先决定活动的顺序，再逐步安排具体时间。

Wanderlog 的行程支持在添加地点后单独设置开始和结束时间，Mindtrip 也强调灵活行程。

建议修改： FR-05、BR-02、PlanItem 数据模型和 P05 工作区。增加日期内排序、可选时间、固定时间标识，以及针对不同精确程度的检查规则。

### 2. 查看者无法提出新的候选地点，和产品目标冲突

明确的需求不一致

`00-设计依据与范围` 第 4 节的目标明确写着：

> 每位成员能独立贡献地点和偏好。

但 `01` 的权限矩阵却规定，查看者不能添加候选地点，而邀请默认授予查看权限。



现实中的场景可能是：朋友收到邀请，只想推荐一家餐厅，并不愿意承担编辑整份行程的责任。

他现在却需要组织者先授予编辑权限。

我建议将提出想法和修改正式行程分开授权：

| 操作      | 普通参与者 | 行程编辑者  |
| ------- | ----- | ------ |
| 添加候选地点  | 允许    | 允许     |
| 发表偏好和评论 | 允许    | 允许     |
| 投票      | 允许    | 允许     |
| 修改行程时间  | 不允许   | 允许     |
| 编辑方案预算  | 不允许   | 允许     |
| 生成定稿    | 不允许   | 按组织者权限 |

这里可以保留“查看者”的名称，也可以改成“参与者”。关键是能够贡献想法，不意味着拥有修改他人安排的权限。

此外，当前邀请默认单次使用。如果组织者希望直接在四人微信群中发送一条邀请链接，流程会比较繁琐。建议支持带人数上限、有效期且可撤销的多人邀请链接。

### 3. 所有活动默认全员参加，不够符合真实旅行

重要产品能力缺口

文档明确将分组活动和细分行程参与者放在 P2，因此这不是遗漏，而是主动控制范围的结果。



但从真实产品角度，它是比较大的限制。

例如四个人上午一起参观博物馆，下午两个人去购物，另外两个人休息。如果系统仍然认为所有人都参加购物活动，会产生两个问题。

首先，不参加购物的人，其不可用时间也可能触发冲突。其次，购物或门票费用会按照四个人计算，导致预算不准确。

建议不必立即实现复杂的多路线规划，可以先增加每项活动的参与成员字段，默认全选，并允许手动取消。

然后让费用和个人约束只针对实际参与该活动的人计算。

这能够显著增加产品的现实适用性，但涉及数据模型和检查算法变更，需要单独评估工作量。

### 4. 投票可能因为无关修改而失效

高优先级逻辑问题

这是我认为当前设计中最值得优先检查的业务规则之一。

`01-BR-06` 将议题绑定方案版本。方案日程、费用、预算等发生变化时，相关开放议题就会结束并归档。`03` 采用方案级 revision，也明确承认即使两个人编辑不同活动，也可能出现保存冲突。



例如：

小林发起投票：“是否把周六下午的玄武湖换成室内展馆？”

此时小周修改了周日酒店的预计费用。

如果议题只通过整份方案 revision 判断是否有效，这个不相关的操作也可能使投票结束。

这会显著增加重新发起议题的成本。

建议将议题绑定到实际讨论的对象及其依赖内容，例如活动、替代地点、相关费用与路线。只有这些内容发生实质性改变时，才要求重新确认。成员资格变化则继续按资格规则处理。

同时保留历史证据，避免新版本覆盖旧投票。

### 5. 缺少“预订执行状态”和任务责任人

建议补充到完整产品

文档排除了订票、付款等交易功能，这个决定合理。

但不执行预订，并不代表不应该管理预订信息。

真正出行前，用户仍然需要知道：

| 活动    | 状态      | 责任人 |
| ----- | ------- | --- |
| 高铁票   | 已预订     | 小林  |
| 酒店    | 已预订，待入住 | 小周  |
| 博物馆门票 | 尚未预约    | 小陈  |
| 餐厅    | 待确认人数   | 小林  |

最少应该支持待处理、已确认、已取消三种状态；可以扩展预订链接、截止时间、确认时间和必要的参考信息。

这不需要接入支付系统，却能弥补“计划写好了，但没有真正落实”的问题。

Wanderlog 和 Mindtrip 都将预订资料整合进旅行规划，而不仅提供一个按时间排序的景点清单。

## 三、其他问题与技术细节

下面这些问题也需要处理，其中有些是明确的跨文档不一致，有些是建议增强的产品需求。

| 优先度 | 当前问题                                    | 建议                               |
| --- | --------------------------------------- | -------------------------------- |
| 高   | `01` 允许编辑者关闭议题，但 `03` API 限定发起者或组织者关闭   | 统一议题关闭权限，避免前后端合同不一致              |
| 高   | 交通估算模型没有明确记录计划出发时刻                      | 将出发日期、时间和交通方式纳入路线估算的输入及失效条件      |
| 高   | 旅途中修改已定稿安排仍需重新建立修订草稿、检查和定稿              | 设计快捷修订入口，保留安全检查和版本记录，但减少操作步骤     |
| 中高  | `ActualExpense` 可以关联方案预计费用，但没有明确的定稿版本锚点 | 明确实际费用如何与指定定稿快照对照，避免新旧方案费用混淆     |
| 中高  | 只采用站内聚合通知                               | 对待投票、重要变更、新定稿提供用户可选择的提醒渠道        |
| 中   | 地点主要靠搜索或手工添加                            | 支持粘贴攻略、地图、餐厅页面链接并作为候选来源          |
| 中   | 旅途中网络不可用时主要依赖提前导出 PDF                   | 考虑缓存最近一次定稿的只读行程，不必实现离线多人编辑       |
| 中   | 旅行关闭和重新打开的业务状态尚未冻结                      | 同步补充到 `01`、`03`、`04` 的权限、接口与验收规则 |

其中，议题关闭权限的不一致可以直接从 `01` 权限矩阵与 `03` API 合同确认。



还有一个技术措辞需要调整：文档要求所有第三方 API 密钥只能存放在服务端。对需要保密的 Web Service 凭据，这个原则正确；但某些浏览器地图 SDK 本身使用受域名、API 范围限制的客户端密钥。最终应按选定供应商的要求分别管理，不能把所有凭据一概视为同一种秘密。

## 四、现有文档哪些设计应该保留？

我不建议全面重写。下面这些设计判断是有价值的：

区分候选、行程和定稿

用户知道收藏不意味着承诺，已保存也不意味着已经确认。

未知信息不当成正常数据

未知票价不等于免费，未知路线不等于无冲突。这应作为强制业务规则保留。

投票、决定和执行彼此独立

能避免用户误以为一次投票立即修改了全组行程。

服务端版本校验和失败恢复

至少保证不会因为两个客户端同时保存而静默覆盖已提交内容。首版使用粗粒度版本校验可以接受，再根据真实协作测试决定是否细化。

为拖拽提供非拖拽替代

对手机、键盘和无障碍使用至关重要。

文档还正确区分了测试计划与实际研究结果，没有把尚未执行的访谈或可用性测试写成已验证结论。这一点也应该继续保持。

## 五、按照三人开发团队，我建议怎样安排？

如果以 2026 年 12 月底为完成目标，不能把所有对真实产品有价值的功能都塞入这次课程项目。

建议按以下方式修订优先级：

| 阶段         | 目标            | 范围                                |
| ---------- | ------------- | --------------------------------- |
| 第一阶段：核心可用  | 让朋友真正完成一次共同规划 | 创建旅行、邀请、地点收集、偏好、灵活行程、基本交通/预算、协作同步 |
| 第二阶段：共同决定  | 让不同意见能够形成明确结论 | 评论、轻量议题、投票、方案比较、定稿、修订             |
| 第三阶段：可执行交付 | 让计划可以真正带去旅行   | 真实地点/路线接入、预订状态、移动查看、导出、实际费用、完整测试  |
| 后续增强       | 改进复杂旅行体验      | 分组行程、个人预算、费用分摊、自动优化、复杂离线协作        |

这是一份建议的实现顺序。因为你们文档已将原有 P0/P1 全部列为最终必交，若正式减少范围，仍需要小组和课程要求确认，不能擅自将已承诺的功能改为选做。

## 六、我最建议做的 HCI 用户测试

现有 `04` 的测试计划已经比较详细，但可以补充几个更接近真实使用情境的任务。

| 测试任务                      | 想验证什么                    |
| ------------------------- | ------------------------ |
| 给四位用户一个尚未确定日期、只收集了攻略的旅行想法 | 用户能否自然开始规划，而不是被日期和时间表单卡住 |
| 让只有查看权限的成员推荐餐厅            | 是否能够贡献想法而不要求编辑整份行程       |
| 让两位成员同时修改不同活动，另一位参与投票     | 版本控制和议题失效是否产生不必要的打断      |
| 让一人不参加某项活动，其余成员仍希望前往      | 系统能否表达局部参与，不产生错误的时间与费用冲突 |
| 模拟出行当天降雨，需要把已预订活动换成室内项目   | 用户能否快速完成修改、确认并让其他人看到有效版本 |

特别建议增加一个对照条件：微信群 + 地图收藏 + 共享表格。这是用户很可能真正采用的替代方案，而不只是拿你们的工具和一张纸对比。

你们需要验证的不只是“这个功能能不能操作”，还包括“用户使用它是否真的比现有方式省事”。

## 七、我建议重新明确产品的核心体验

结合前面的分析，我会将产品主流程调整为：

1\. 灵感与候选

收集地点、攻略链接、餐厅和住宿想法，不要求立即决定时间

2\. 共同筛选

查看成员偏好、可参加时间、初步预算

3\. 灵活编排行程

先分配日期和顺序，再设置精确时间、锁定已预订活动

4\. 检查、讨论与修改

自动提示影响，在有分歧的地方就地讨论并记录决定

5\. 确认并落实

发布当前行程、明确待预订事项和负责人

6\. 出行与临时调整

手机导航、快捷修订、查看最新有效安排和实际费用

这样，用户首先接触的是轻量化旅行规划，只有真正遇到不同意见、时间冲突或定稿需求时，才需要使用更正式的协作机制。

这也更适合你接下来用 Google Stitch 设计原型：核心工作区应该同时支持「未排时间的日程卡片」「可自由调整的活动」「固定预约活动」三种状态，而不是只有密密麻麻的严格时间轴。

## 最终判断

我不认为你们缺少总体需求框架。实际上，现有设计对并发、安全、异常恢复和可验证性考虑得比较充分。

真正需要调整的是：让产品从一个严格的多人行程管理系统，变成一个让朋友愿意主动使用的共同规划工具。

如果只能优先修改四件事，我会选择：灵活排程、普通成员贡献权限、精准的投票失效范围、预订状态管理。它们对真实使用体验的影响，比继续增加 AI 推荐、自动路线优化或精细动画更大。

完成这几项调整，再确定 Stitch 原型的核心页面和交互状态，会比现在直接把 12 张页面全部做出来更有价值。
