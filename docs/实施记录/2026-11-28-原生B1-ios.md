# 2026-11-28 原生 B1（iOS）：白板数据与同步

依据：[11-原生端功能对齐](../设计文档/11-原生端功能对齐.md) 第 3、4 节与 B1 工作包、「本轮并行要点」B1 条；[10-白板](../设计文档/10-白板.md) 第 2、3.1、8、13 节。分支 `native/B1-ios`（从 `dev` 60438bb 拉出），规则对齐网页 `main` 3d5a2e4。本包只做数据层与白板列表数据，不做画布（B2）。

## 修改

- **规则移植（新文件 `mobile/ios/Journey/BoardSync.swift`）**
  - `BoardPending`：`board-pending.js` 的 `PENDING_TTL`、`mergeExpected`、`reconcilePending`、`isStaleResponse`。待确认修改按网页的 `Map` 语义保留插入顺序（`Changes`），`isStaleResponse` 按 JS 的 `Number()`、真值判断与缺失 / null 区分移植。
  - `BoardItems`：`board-sync.js` 的 `normalizeBoardItem`、`cleanBoardItemPatch`，`board.js` 的 `BOARD_STYLE_KEYS`、`cleanBoardStylePatch`、`nextBoardStyle`，以及 `patchBoardItem` 的本地副本合并（content / frame 合并，style 合并或替换）。
  - `BoardList`：`Board.jsx` 的白板列表（active 的 `board`，按 `order`、再按 id 的 `localeCompare` 排序；Swift 按 Unicode 根排序规则对 `[A-Za-z0-9_-]` 实现同样的顺序），无白板时给出 `default-board`（主白板），当前白板的选取，新建白板的 `order` 与标题，删除 / 恢复权限（与服务端一致）。
- **数据层（新文件 `mobile/ios/Journey/BoardStore.swift`）**，对应 `useBoard`（不含 presence，B8 再做）：
  - 打开白板：先显示本机缓存，再按缓存 cursor `?since=` 增量读取；缓存的 epoch 与服务器不同则不带 since 全量重读并替换缓存。
  - `refresh()`：增量读取；同 epoch 合并变化项，不同 epoch 丢弃 cursor 全量重读；比屏幕上更旧的回复（同 epoch、cursor 更小）丢弃。每块白板同一时间只有一个读取，期间再请求的刷新在其后补跑一次，调用方等到补跑结束。
  - 刷新时机：打开白板、回到前台（`UIApplication.willEnterForegroundNotification`）、本机白板操作被服务器接受之后。`refresh()` 也是 SSE `change` 的入口：N2 合入 `dev` 后在收到 `change` 时调用 `store.boards.refresh()` 即可（本包合并时 N2 尚未进入 `dev`）。
  - 写入：`add` / `patch` / `delete` / `restore` 乐观更新本地副本并记入待确认修改，经现有离线队列上传（与其他修改同一队列、保持顺序）；`patch` 只发送变化的逻辑组，style 发送合并后的完整值、经 `BOARD_STYLE_KEYS` 清洗，frame 规整为 `{x,y,w,h,rotation,scale}`。排队失败（本机存储失败、旅程已切换）时撤回本地修改。
  - 缓存：按账号隔离，存于账号缓存旁的 `<账号>.boards/<旅程>/<白板>.json`（`{cursor,epoch,items}`）。切换旅程或账号时关闭当前白板。
  - 白板层面的操作：`createBoard`（`白板 N`、order = 最大值 + 1）、`renameBoard`、`setBoardBackground`、`deleteBoard`（至少保留一块，仅有权限者）、`restoreBoard`，供 B9 使用。
- **共用文件只做接线**
  - `JourneyStore.swift`：上传队列接受白板对象操作「只有 receipt、没有 snapshot」的回复（原先会当作未确认无限重试）；过期 generation 的删除 / 恢复返回 `receipt.changed=false` 时按成功出队；白板操作被接受后通知 `BoardStore` 读取变化；放弃某旅程的待上传修改后清掉该旅程的白板缓存并重读当前白板；提供白板缓存目录；持有 `boards`。
  - `Models.swift`：`SnapshotProjection` 跳过 `objectType = boardItem` 的排队操作（与网页 `optimistic` 一致，主快照不含 boardItem）。
- **共享用例**：`mobile/tools/generate-fixtures.mjs` 新增 `board-sync.json`（35 条，来源 `app/src/board-pending.js`）：`mergeExpected` 9 条、`isStaleResponse` 13 条、`reconcilePending` 13 条（固定 `now`，含恰好 `PENDING_TTL`、超过 1 ms、数字容差 0.01、数字与字符串、缺失与 null、按组逐项比较、数组整体比较、本地删除 / 恢复、服务器尚未返回的新对象按修改顺序追加）。`reconcilePending` 会原地修剪 `pending`，用例把 Map 记为条目数组、结果记为 `{items, pending}`。
- **原生单测（新文件 `mobile/ios/JourneyTests/BoardSyncTests.swift`）**：回放 `board-sync.json` 与 `board-geometry.json` 中的 `cleanBoardStylePatch`、`nextBoardStyle`；`normalizeBoardItem`、`cleanBoardItemPatch` 与 `patchBoardItem` 本地合并的期望值由网页 `board-sync.js` 的函数直接算出（模块因依赖 React 与浏览器同步层无法在 Node 导入，测试里写明来源）；`BoardStore` 用模拟服务器覆盖首次读取与缓存、增量与 epoch 变化、过期回复、离线排队与重放、只含 receipt 的回复、待确认修改与 TTL、过期 generation 的删除 / 恢复、`BOARD_FULL`、放弃修改后重读、切换旅程与账号；另有对联调服务的集成测试（环境变量控制，见下）。
- **接口文档**：`app/CONTRACT.md` 按 `main` 代码补充 items 接口返回的对象字段（无 `tripId` / `expressions`，有 `changedCursor`，按 `changedCursor` 升序）、只返回 receipt 的判定（`objectType` 为 boardItem 或目标对象是 boardItem）与 receipt 字段，`changed=false` 不推进 cursor。

## 与网页的差异与说明

- JSON 在 Swift 中是无序字典，`sameValue` 对嵌套对象做与键顺序无关的深比较；网页用 `JSON.stringify` 比较，键顺序不同会多保留本地副本至多 15 秒。共享用例中的嵌套对象键顺序一致，结果相同。
- 待确认修改只在内存中（与网页相同）；应用重启后若队列里仍有白板修改，重放时可能短暂显示服务器上的旧副本，直到修改被接受后的刷新。
- `BOARD_FULL`（409）：与网页一样，该操作在队列中标为受阻并暂停该旅程之后的上传；iOS 弹出服务器的提示（「每块白板最多添加 2000 个对象」/「每段旅程最多创建 20 块白板」）。**风险**：iOS「保存与同步」页目前没有网页那样的「放弃这些修改」入口（`JourneyStore.discard` 已有但无界面），受阻后只能重试，后续修改会一直等待。建议另开任务补齐放弃入口（影响所有受阻类型，不只白板）。
- 网页白板页在快照没有任何 active 白板时会提交一次 `create board default-board`；本包按 B1 说明只把 `default-board` 当作白板处理、依靠服务端在读取 items 时惰性补齐，不主动提交，留给有白板界面的 B2 / B9 决定。
