# Journey 运行维护

域名为 `journey.jscloud.wang`，应用监听 `127.0.0.1:4177`，复用 nginx 的 443 入口。账号使用手机号或邮箱加密码，生产环境不配置 SMTP 或短信发送凭据。账号先注册，再用命令赋予首位运维管理员身份。

main 自动发布的工作流、权限配置、失败恢复及验收记录见[GitHub 自动部署](GitHub自动部署.md)。日常升级由 GitHub Actions 完成。

## 本地构建与发布包

在仓库根目录执行。需要本地 Node 与 npm、tar，服务器只需要 Node.js 22.22.1，不运行 npm。

```sh
cd app
npm ci --cache ../.local/npm-cache
npm test
node ops/package-release.mjs 2026-10-13-01
cd ../.local/releases
shasum -a 256 -c 2026-10-13-01.tar.gz.sha256
tar -tzf 2026-10-13-01.tar.gz
```

打包脚本先构建，再在隔离 stage 中执行 `npm ci --omit=dev --ignore-scripts --cache <仓库>/.local/npm-cache`。生产依赖为 JavaScript 包。归档包含 `node_modules`、`server/**`、`src/domain.js`、`dist/**`、`ops/**`、包锁文件及 `release-manifest.json`，并在归档旁生成 manifest 和 SHA-256 文件。发布 ID 不允许覆盖。打包清单按路径选入，不收集 `.local`、数据库、环境文件或地图服务密钥。`gitCommit` 记录当时 HEAD；发布前应提交待发布源文件，确保版本来源可追溯。

## 首次安装

首次安装已于 2026-10-13 执行，当前 release 为 `2026-10-13-01`。以下保留安装过程供重建使用。升级已有实例按本文“备份、恢复与回滚”操作。

```sh
ssh tencent 'systemctl list-units --type=service --all | rg "l4d2|left4dead"; ps -eo pid,lstart,args | rg "srcds|left4dead"'
# 对上一步识别的每个游戏 unit 读取：
ssh tencent 'systemctl show l4d2.service -p MainPID -p ActiveEnterTimestamp -p ExecMainStartTimestamp -p NRestarts'
```

`l4d2.service` 应替换为查询得到的真实名称。此过程只读，不重启游戏。应用 CPU 限额 40%、CPUWeight 10、IOWeight 10、Nice 10，内存软限额 384 MiB、硬限额 512 MiB；备份 CPU 限额 10%、CPUWeight 1、Nice 19、磁盘 I/O idle。

已存在的 `journey` 用户无需重复创建。服务器已有 `/usr/bin/node`，版本为 Node.js 22.22.1。运行 `sudo -u journey /usr/bin/node --version` 确认为 `v22.22.1`，运行时由 root 管理，journey 只读、可执行。

```sh
sudo install -o root -g journey -m 0640 /opt/journey/current/ops/journey.env.example /etc/journey/journey.env
sudoedit /etc/journey/journey.env
# 将本机已有高德配置安全上传后，保存为 /etc/journey/amap.json，root:journey 0640。
# 首次生成密钥；文件已存在时保留，轮换密钥会改变历史备份的解密条件。
sudo sh -c 'umask 077; set -C; head -c 32 /dev/urandom > /etc/journey/backup.key'
sudo install -o root -g root -m 0644 /opt/journey/current/ops/journey.service /etc/systemd/system/journey.service
sudo install -d -o root -g root -m 0755 /usr/local/libexec/journey
sudo install -o root -g root -m 0644 /opt/journey/current/ops/backup.mjs /usr/local/libexec/journey/backup.mjs
sudo install -o root -g root -m 0644 /opt/journey/current/ops/journey-backup.service /etc/systemd/system/journey-backup.service
sudo install -o root -g root -m 0644 /opt/journey/current/ops/journey-backup.timer /etc/systemd/system/journey-backup.timer
sudo systemctl daemon-reload
```

## 独立 nginx 站点与证书

已签发证书位于 `/root/.acme.sh/journey.jscloud.wang_ecc/`。用 acme.sh 的 install-cert 注册安装路径及 reload hook；现有 `l4d2-cert-renew.timer` 每天运行 acme cron，覆盖该证书。无需新增续签 timer。不要直接让 nginx 依赖 acme.sh 内部工作文件。

```sh
sudo install -d -o root -g root -m 0700 /etc/nginx/journey-tls
sudo /usr/local/bin/acme.sh --home /root/.acme.sh --install-cert -d journey.jscloud.wang --ecc \
  --fullchain-file /etc/nginx/journey-tls/fullchain.pem \
  --key-file /etc/nginx/journey-tls/privkey.pem \
  --reloadcmd 'nginx -t && systemctl reload nginx'
sudo chmod 0600 /etc/nginx/journey-tls/privkey.pem
sudo install -o root -g root -m 0644 /opt/journey/current/ops/journey.nginx.conf /etc/nginx/sites-available/journey
sudo ln -s /etc/nginx/sites-available/journey /etc/nginx/sites-enabled/journey
sudo nginx -t
sudo systemctl reload nginx
curl --fail https://journey.jscloud.wang/api/health
sudo ss -lntp
sudo systemctl status journey.service journey-backup.timer --no-pager
```

模板仅声明独立的 `server_name journey.jscloud.wang` 和已有 443 入口。部署前检查 nginx 是否加载 `sites-enabled/*`，已有同名站点应先审查，其他站点配置保持原样。反向代理禁用缓冲和缓存，使用 HTTP/1.1，覆盖转发地址，SSE 心跳间隔小于代理读取超时。应用仅信任 loopback 代理。公网防火墙无需增加端口。

## 首位管理员

先在网页使用自己的手机号或邮箱注册。邮箱按小写存储；11 位大陆手机号存储为带 `+86` 前缀的规范形式，例如 `+8613812345678`。`admin.mjs` 参数必须是已注册的规范标识。该命令提升运维身份，旅程成员角色继续由旅程权限管理。

```sh
sudo systemctl stop journey.service
sudo -u journey sh -c 'set -a; . /etc/journey/journey.env; set +a; cd /opt/journey/current; /usr/bin/node server/admin.mjs "registered@example.com"'
sudo systemctl start journey.service
```

## 备份、恢复与回滚

每天 04:35 加 0–15 分钟随机延迟进行备份。备份先通过 Node `node:sqlite` 在线 backup 复制业务库，再复制独立权限账本；每份数据库用独立随机 IV、AES-256-GCM 和类型 AAD 加密，目录包含 `main.enc`、`security.enc`、`manifest.json`。备份完成后清理备份目录中超过 30 天的已完成 `backup-*` 目录。`/var/lib/journey/security.sqlite` 始终作为最新在线账本保留，保留期清理只作用于加密历史副本。应在受控离线位置另外保管备份密钥；移动备份时一起保留三个文件。

```sh
sudo systemctl start journey-backup.service
sudo journalctl -u journey-backup.service -n 30 --no-pager
sudo find /var/backups/journey -maxdepth 2 -type f -printf '%m %u %p\n'
```

同机恢复必须停止应用和备份任务，并保留最新 `security.sqlite` 及其 WAL/SHM。恢复命令同时校验服务处于 inactive/failed 且 MainPID 为 0，缺少 `--service-stopped` 或最新账本时拒绝恢复。恢复只替换业务库；历史 security 密文也先验证完整性，但不会安装。当前业务库先通过 SQLite backup 保存为相邻 `.bak-<时间>-<随机值>` 文件，再检查点旧 WAL、原子替换业务库。应用重启时重放当前账本，继续执行永久清除、成员移除、邀请撤销和会话撤销，并推进同步 epoch。

```sh
sudo systemctl stop journey-backup.timer journey-backup.service journey.service
sudo systemctl show journey.service -p ActiveState -p MainPID
sudo sh -c 'set -a; . /etc/journey/journey.env; set +a; cd /opt/journey/current; /usr/bin/node ops/backup.mjs restore /var/backups/journey/backup-具体目录 --service-stopped'
sudo chown journey:journey /var/lib/journey/journey.sqlite
sudo systemctl start journey.service
curl --fail http://127.0.0.1:4177/api/health
sudo systemctl start journey-backup.timer
```

root 恢复产生的主库要交回 journey 所有权。恢复输出的 `.bak-*` 用于人工回退业务数据，按敏感业务库管理，确认恢复成功后清理。不能用历史权限副本覆盖当前账本；如果最新账本丢失，暂停恢复并从权威最新副本恢复该账本后再继续，历史副本不满足最新权限边界。

代码升级用新的 release ID 解包到新目录，复用上述所有权设置。切换前记录 `readlink /opt/journey/current`，执行一次备份；停止应用后原子切换链接。首次安装后升级命令示例：

```sh
sudo systemctl start journey-backup.service
readlink /opt/journey/current
sudo systemctl stop journey.service
sudo ln -s releases/新的版本 /opt/journey/current.next
sudo mv -Tf /opt/journey/current.next /opt/journey/current
sudo systemctl start journey.service
curl --fail http://127.0.0.1:4177/api/health
curl --fail https://journey.jscloud.wang/api/health
```

代码回滚同样先停机，将 `current` 链接原子切回已记录的旧 release。当前迁移采用增加表的方式，回滚前仍应核对目标版本读取现有业务库的兼容性；需要恢复业务数据时使用上面的加密恢复流程，保留最新权限账本。维护完成后再次读取游戏服务的 PID、启动时间和重启次数，与维护前记录比较。

## 错误定位

响应头 `X-Request-Id` 和失败 JSON 的 `requestId` 由服务端生成。nginx 访问日志只记录时间、请求方法、HTTP 状态、耗时和上游请求 ID，不保存 URL、查询字符串、Cookie 或请求体。应用仅在 500 错误时记录请求 ID、方法、路由模板、状态与错误码；完整错误原文及堆栈不写入生产日志。

```sh
sudo journalctl -u journey.service --since "30 minutes ago" --no-pager
sudo tail -n 50 /var/log/nginx/journey.access.log
```

## 首次上线回退到原服务器状态

当前为首次正式旅行版本。已有三个网站配置保持原文件，副本存于 `/var/backups/journey/deployment-2026-10-13-01/`，发布包 SHA-256 同目录保留。若需要撤下旅行站点，执行下面的范围限定操作；数据库、发布目录、证书和加密备份继续保留。

```sh
sudo systemctl disable --now journey-backup.timer
sudo systemctl stop journey-backup.service journey.service
sudo systemctl disable journey.service
sudo rm /etc/nginx/sites-enabled/journey
sudo nginx -t && sudo systemctl reload nginx
```

重新上线可恢复该 nginx 链接、校验配置并重载，再启用 `journey.service` 与 `journey-backup.timer`。上述操作只涉及旅行服务及其站点链接，L4D2 和控制台 unit 无需操作。
