# 11｜原生端功能对齐

> 状态：计划（2026-11-22 定）　｜　适用：`mobile/android`、`mobile/ios`
> 本文件同时是给原生开发 agent 的任务说明。开工前先读完第 1–3 节，再读自己负责的工作包。

## 1. 决定（2026-11-22，用户确认）

| # | 事项 | 决定 |
| --- | --- | --- |
| 1 | 对齐目标 | iOS、Android 的功能与网页端**稳定版本（`main`）**对齐，包括白板 |
| 2 | 白板实现方式 | **原生重写**（Android Compose，iOS SwiftUI），不嵌入网页。取代 [10-白板](10-白板.md) 第 14 节第 4 项「原生端只做基础可用」 |
| 3 | 迭代顺序 | 新功能和改版**先在网页端迭代**，合并进 `main` 成为稳定版本后，再由原生端补齐。原生端不追 `dev` 上未发布的改动 |
| 4 | 对齐口径 | 功能、数据和规则一致；交互形式按平台惯例（系统面板、菜单、弹窗、手势），不照搬网页像素。白板小组件的版式按 [10-白板](10-白板.md) 第 5 节，与网页并排比对 |

## 2. 对齐基线

| 项 | 值 |
| --- | --- |
| 原生端上次对齐的网页版本 | `fef96de`（2026-11-04，行程卡片与跨端链接） |
| 本轮对齐目标 | `origin/main` = `bb38ac1`（2026-11-13 发布，含白板） |
| 两者之间网页端改动 | `git log fef96de..bb38ac1 -- app/src app/server app/CONTRACT.md`（22 个提交，主体是白板） |

**以后每次补齐的做法**：`main` 有新发布后，开一个「原生补齐」任务：

1. `git log <上次基线>..origin/main -- app/src app/server app/CONTRACT.md design/tokens.json`，列出所有用户能感知的改动；
2. 判断每条是网页专属（CSS、DOM、浏览器兼容，如 2026-11-22 移动端网页修复的大部分条目）还是原生也要做；
3. 原生要做的按第 5 节的方式拆包；完成后把本节第一行改为新的基线。

`dev` 上的改动（例如 2026-11-22 移动端网页修复）进入 `main` 之前不纳入对齐。

## 3. 开发规则（所有工作包）

- **数据与接口以 `app/CONTRACT.md` 为准，规则以网页代码为准**：两者不一致时以 `main` 上的代码为准，并在工作包里修正 `app/CONTRACT.md`。不新增或修改服务端接口；确实需要时停下报告。
- **规则逻辑移植，不重新发明**：排序（`orderedActivities`）、路程匹配（同时匹配 `fromId` 与 `toId`）、时区（按目的地时区，不用设备时区）、小组件数据（`widgetDeps` / `widgetModel`）、富文本清洗（`sanitizeRichText`）、几何（`scaled`、`simplify`、`contentBounds`）都按网页实现移植为 Kotlin / Swift，并用第 4 节的共享用例校验两端结果一致。
- **分支**：每个工作包、每个平台一个分支 `native/<包号>-<android|ios>`，从 `dev` 拉出，完成后合回 `dev`。不推送、不合并 `main`。
- **提交信息**写清改了什么，**不加 AI 署名行**；修改与验证写入 `docs/实施记录/<日期>-原生<包号>.md`；完成后更新本文件第 7 节进度表。
- **完成标准**（每个包）：
  - Android：`cd mobile/android && ./gradlew testDebugUnitTest lintDebug assembleDebug` 通过；
  - iOS：按 `mobile/README.md` 的 `xcodebuild` 构建通过，`JourneyTests` 全部通过；
  - 第 4 节的共享用例在该平台全部通过；
  - **双向互通**：用 `node mobile/tools/dev-server.mjs --seed` 起服务，同一旅程在网页端与原生端互相修改，两边显示一致；
  - 浅色、深色各截图，与网页同一场景并排存入 `.local/evidence/<MMDD>-native-<包号>/`。
- 不为了通过而跳过、放宽或删除测试。

## 4. 共享用例（第一个工作包 N0 建立）

仿照现有的 `mobile/fixtures/routes.json`，新增脚本 `mobile/tools/generate-fixtures.mjs`：直接 `import` 网页端模块，对一组输入算出结果，写成 JSON 放进 `mobile/fixtures/`。两端单元测试读取这些 JSON，断言原生实现的输出与网页完全一致。至少包括：

| 文件 | 来源 | 内容 |
| --- | --- | --- |
| `rich-text.json` | `app/src/rich-text.js` | `sanitizeRichText`、`richTextToPlain`、`plainToRichText` 的输入输出，覆盖白名单内外标签、颜色、勾选清单、恶意属性 |
| `board-geometry.json` | `app/src/board.js` | `scaled`（各锚点）、`simplify`、`contentBounds`、`center`、`toWorld` / `toScreen`、`cleanBoardStylePatch` |
| `board-widgets.json` | `app/src/board-widgets.js` | 一份含活动、路程、收藏、预设、费用、已删除对象的快照，对 8 种小组件逐一给出 `widgetDeps`、`widgetModel`、`widgetSize`、`placeGroups` 的结果（固定 `now` 与时区） |
| `itinerary.json` | `app/src/domain.js` 等 | `orderedActivities`、日期与时区相关函数 |

网页端相关函数改动后要重新生成；`npm run check` 之外再加一步比对（N0 里接进 `scripts/`，与 token、时区检查同样方式）。

## 6. 原生端容易做错的地方

10-白板第 13 节全部适用，另外：

1. 用设备时区算「今天」、倒计时或当地时间。一律用旅程目的地时区。
2. 把小组件显示的数据存进 boardItem。只存 id，每次现算。
3. 富文本自己拼 HTML、不经清洗就上传或显示。上传前、显示前都按白名单清洗，并通过往返用例。
4. 收到新 `epoch` 仍沿用旧 cursor。必须全量重读。
5. 缩放笔迹只改 frame。frame 与 points 要一起按比例提交。
6. 笔迹单独一层。笔迹与贴纸共用同一 z 序。
7. 每次拖动都发一个操作。拖动过程走 presence，松手后再提交一次 frame。
8. 把快照里认不出的对象显示出来或弄崩。未知 `kind`、未知 content 类型、未知小组件类型一律安全忽略或显示为占位。
9. 原生端提前实现 `dev` 上尚未发布的网页改动。只追 `main`。
