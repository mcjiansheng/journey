## 3. 开发规则（所有工作包）

- **数据与接口以 `app/CONTRACT.md` 为准，规则以网页代码为准**：两者不一致时以 `main` 上的代码为准，并在工作包里修正 `app/CONTRACT.md`。不新增或修改服务端接口；确实需要时停下报告。
- **规则逻辑移植，不重新发明**：排序（`orderedActivities`）、路程匹配（同时匹配 `fromId` 与 `toId`）、时区（按目的地时区，不用设备时区）、小组件数据（`widgetDeps` / `widgetModel`）、富文本清洗（`sanitizeRichText`）、几何（`scaled`、`simplify`、`contentBounds`）都按网页实现移植为 Kotlin / Swift，并用第 4 节的共享用例校验两端结果一致。
- **分支与工作目录**：每个工作包、每个平台一个分支 `native/<包号>-<android|ios>`，从本地 `dev` 拉出，在独立的 git worktree 里开发（`git worktree add ../journey-<包号>-<平台> -b native/<包号>-<平台> dev`）。不要在主目录（`dev` 所在的工作目录）里切换分支或合并，也不要进入别的 agent 的工作目录。完成后按 3.2 节合回 `dev`；不合并 `main`。
- **提交信息**写清改了什么，**不加 AI 署名行**；修改与验证写入 `docs/实施记录/<日期>-原生<包号>-<平台>.md`（两个平台分开写，避免冲突）；完成后只更新本文件第 7 节进度表中自己那一格。不改 `STATE.md`，一轮结束后由协调者统一重写。
- **完成标准**（每个包）：
  - Android：`cd mobile/android && ./gradlew testDebugUnitTest lintDebug assembleDebug` 通过；
  - iOS：按 `mobile/README.md` 的 `xcodebuild` 构建通过，`JourneyTests` 全部通过；
  - 第 4 节的共享用例在该平台全部通过；
  - **双向互通**：按 3.1 节起联调服务，同一旅程在网页端与原生端互相修改，两边显示一致；
  - 浅色、深色各截图，与网页同一场景并排存入主目录的 `.local/evidence/<MMDD>-native-<包号>-<平台>/`（工作目录的 `.local/` 会随 worktree 删除）。
- 不为了通过而跳过、放宽或删除测试。

## 4. 共享用例（第一个工作包 N0 建立）

仿照现有的 `mobile/fixtures/routes.json`，新增脚本 `mobile/tools/generate-fixtures.mjs`：直接 `import` 网页端模块，对一组输入算出结果，写成 JSON 放进 `mobile/fixtures/`。两端单元测试读取这些 JSON，断言原生实现的输出与网页完全一致。至少包括：

| 文件 | 来源 | 内容 |
| --- | --- | --- |
| `rich-text.json` | `app/src/rich-text.js` | `sanitizeRichText`、`richTextToPlain`、`plainToRichText` 的输入输出，覆盖白名单内外标签、颜色、勾选清单、恶意属性 |
| `board-geometry.json` | `app/src/board.js` | `scaled`（各锚点）、`simplify`、`contentBounds`、`center`、`toWorld` / `toScreen`、`cleanBoardStylePatch` |
| `board-widgets.json` | `app/src/board-widgets.js` | 一份含活动、路程、收藏、预设、费用、已删除对象的快照，对 8 种小组件逐一给出 `widgetDeps`、`widgetModel`、`widgetSize`、`placeGroups` 的结果（固定 `now` 与时区） |
| `itinerary.json` | `app/src/domain.js` 等 | `orderedActivities`、日期与时区相关函数 |

网页端相关函数改动后要重新生成；`npm run check` 已包含 `fixtures:check`，用例过期会失败。

**用法（N0 已建立，2026-11-22）**：

- 每条用例是 `{ fn, args, result }`（或 `error`），多个模块合在一个文件时另有 `module`。参数 `"$snapshot"` 指文件顶层的 `snapshot`，`"$fn:simplify"` 指调用方自己传入的 `simplify` 移植版。
- 两端已有读取工具：Android `SharedFixturesTest.kt` 的 `Fixtures.load / cases / same`，iOS `SharedFixturesTests.swift` 的同名方法。`same` 做深比较，数字允许 1e-9 误差。
- 移植一个函数后，在同一文件里加一个测试，遍历 `Fixtures.cases(文件, "函数名")` 并逐条比对。目前已接上的：`orderedActivities`、`routeSignature`、已删除列表过滤。
- iOS 新增测试文件或 fixture 后运行 `python3 mobile/ios/generate-project.py` 重新生成工程。
- 部分结果依赖 `Intl`（日期文字、时区），由 Node 的 ICU 数据计算；若不同机器上 `fixtures:check` 结果不一致，以 CI 所用 Node 版本重新生成。

### 本轮并行要点（N1–N3、B1，2026-11-27）

四个包同时开发时，下面列出的「共用文件」会被两个包同时改。新逻辑放进新文件，共用文件里只做接线，减少 3.2 节的冲突。

**N1 小功能**
- 共享用例：`place-information.js` 没有依赖，在 `generate-fixtures.mjs` 增加 `place-information.json`（`normalizePlaceInformation`、`safePlaceUrl`），两端按用例比对。
- 照代码移植并写原生单测（不能在 Node 导入）：「回到今天」「下一项」的判定在 `Itinerary.jsx` 900 行附近，按旅程时区取今天和当前时刻，下一项是当天第一条精确时间、尚未结束的活动；邀请链接解析是 `Entry.jsx` 的 `inviteCode`（取 `invite` 参数，否则取路径最后一段）。
- 二维码内容是 `POST /api/trips/:id/invites` 返回的 `url`。生成：iOS 用 Core Image `CIQRCodeGenerator`，Android 需要编码库（如 ZXing core）。扫码：iOS 用 VisionKit `DataScannerViewController`（部署目标 17.0 可用），Android 用 ML Kit 或 CameraX。iOS `Info.plist` 加 `NSCameraUsageDescription`，Android 加相机权限与运行时请求。
- 共用文件：Android `NativeMap.kt`（与 N3）、`MainActivity.kt`（`ItineraryScreen`、`JoinSheet`）、`Management.kt`；iOS `MapViews.swift`（与 N3）、`ItineraryViews.swift`、`JourneyApp.swift`（`JoinView`）、`ManageViews.swift`、`Info.plist`。

**N2 实时同步**
- 网页参考 `sync.js` 610–680 行（`EventSource`、`revoked`、可见性）。服务端只推 `change`（data 为 `{cursor,epoch}`）和 `revoked`，连接建立时立即发一次当前游标。
- 不加依赖：Android 用现有 OkHttp 读流式响应，自己解析 `text/event-stream`（`okhttp-sse` 不在离线仓库）；iOS 用 `URLSession.bytes(for:)` 逐行解析。会话 Cookie 与普通请求相同。
- 每个打开的旅程只保持一条连接（服务端上限每用户每旅程 4 条，网页标签页也算）；断线指数退避重连；进入后台断开（Android 生命周期 `ON_STOP`，iOS `scenePhase`），回到前台重连并补读。`change` 与现有前台刷新走同一个重读入口，避免重复拉取；`revoked` 退出旅程并提示。
- 连接逻辑放新文件（`EventStream.kt` / `EventStream.swift`），提供订阅回调，B1、B8 会用到。单测覆盖事件流解析：分块到达、多行 `data`、注释行、断线重连。
- 共用文件：Android `JourneyStore.kt`、`Api.kt`（与 B1）、`MainActivity.kt`（与 N1）；iOS `JourneyStore.swift`（与 B1）、`JourneyApp.swift`（与 N1）。
- 互通验证：网页改一处，原生不手动刷新即显示；网页把该成员移出旅程，原生退出；断网或切到后台再回来后数据补齐。

**N3 地图筛选与图例**
- 网页参考 `MapView.jsx`：筛选状态在 100 行附近（图层 全部 / 行程 / 收藏，类别，安排状态 全部 / 已安排 / 未安排，标记），`usedPresets` 与过滤在 185–210 行，图例在 1460 行附近；图层为「收藏」时不画路线（366、796 行）。逻辑写在组件里不能在 Node 导入，照代码移植成纯函数（`MapFilter.kt` / `MapFilter.swift`）并写单测，覆盖各筛选维度的组合。
- 控件按平台惯例（Android 底部面板与 Chip，iOS `Menu` 与 sheet），不照搬网页像素。筛选只影响本机显示，不写共享数据。
- 共用文件：Android `NativeMap.kt`（与 N1）、`MapMarks.kt`；iOS `MapViews.swift`（与 N1）。
- 互通验证：网页新增的收藏和预设标记，在原生筛选与图例里正确出现、计数一致。

**B1 数据与同步**
- 网页参考 `board-sync.js`（`useBoard`、`normalizeBoardItem`、`cleanBoardItemPatch`）、`board-pending.js`、`board.js` 的 `BOARD_STYLE_KEYS` 与 `cleanBoardStylePatch`。
- 共享用例：`board-pending.js` 没有依赖，在 `generate-fixtures.mjs` 增加 `board-sync.json`，覆盖 `mergeExpected`、`reconcilePending`（固定 `now`，含超过 `PENDING_TTL` 的情况）、`isStaleResponse`。`board-sync.js` 依赖浏览器模块不能导入，`normalizeBoardItem`、`cleanBoardItemPatch` 照代码移植并写单测；样式清洗已有 `cleanBoardStylePatch` 用例。
- 没有自定义白板时按 `default-board` 处理（服务端在首次读取时惰性补齐）；`epoch` 变化丢弃 cursor 全量重读；过期 generation 的删除 / 恢复返回 `receipt.changed=false` 视为成功；`BOARD_FULL`（409）给出提示。
- 本包只做数据层和白板列表数据，不做画布（B2）。刷新时机：打开白板、回到前台、自己提交之后；合并时 N2 若已进入 `dev`，把 SSE `change` 接到白板增量拉取，否则留好入口。
- 白板代码放新文件（`Board*.kt` / `Board*.swift`）。共用文件：Android `JourneyStore.kt`、`Api.kt`、`Domain.kt`（与 N2）；iOS `JourneyStore.swift`、`Models.swift`（与 N2）。
- 互通验证：本包没有白板界面时，用对联调服务的集成测试证明——网页写入的白板对象原生能读出并规范化，原生提交的操作在网页白板上可见（截网页图）；原生截图一项写明不适用。

## 6. 原生端容易做错的地方

10-白板第 13 节全部适用，另外：

1. 用设备时区算「今天」、倒计时或当地时间。一律用旅程目的地时区。
2. 把小组件显示的数据存进 boardItem。只存 id，每次现算。
3. 富文本自己拼 HTML、不经清洗就上传或显示。上传前、显示前都按白名单清洗，并通过往返用例。
4. 收到新 `epoch` 仍沿用旧 cursor。必须全量重读。
5. 缩放笔迹只改 frame。frame 与 points 要一起按比例提交。
6. 笔迹单独一层。笔迹与贴纸共用同一 z 序。
7. 每次拖动都发一个操作。拖动过程走 presence，松手后再提交一次 frame。
8. 把快照里认不出的对象显示出来或弄崩。未知 `kind`、未知 content 类型、未知小组件类型一律安全忽略或显示为占位。
9. 原生端提前实现 `dev` 上尚未发布的网页改动。只追 `main`。
